## O problema

Eu queria uma lista que mostrasse o que já assisti, o que está pela metade e o que quero ver, atualizada sozinha. Os dados de catálogo vêm de uma API pública, a AniList, que tem limite de uso e já ficou fora do ar várias vezes. **Boa parte do projeto foi aprender a não depender dela.**

## Três decisões e o que elas custaram

<Decisao
  titulo="Validar JWT por JWKS, não por segredo compartilhado"
  contexto="O login é do Supabase; o backend em Go precisa confiar no token sem chamar o Supabase a cada request."
  escolhi="Buscar a chave pública via JWKS e validar o token no próprio backend."
  descartei="Validar com um segredo compartilhado. Funcionava, mas o mesmo segredo precisaria existir em todo serviço que lê o token, e trocá-lo seria manual."
  custo="Uma dependência a mais: se o endereço das chaves não responder, o login deixa de funcionar."
/>

<Decisao
  titulo="Isolamento por usuário no banco, com RLS — não no handler"
  contexto="Todo dado é pessoal. Um filtro por usuário esquecido em um handler vaza a lista de outra pessoa."
  escolhi="Row Level Security no PostgreSQL, amarrado à identidade do token. O banco recusa o que o handler deixar passar."
  descartei="Confiar só no código da aplicação. É mais rápido de escrever, mas um filtro esquecido vira vazamento sem nenhum aviso."
  custo="Cada tabela precisa da sua regra, e entender por que “uma linha sumiu” leva mais tempo no começo."
/>

<Decisao
  titulo="Um interruptor para desligar a API externa, persistido no banco"
  contexto="Quando a AniList fica instável ou o limite de uso estoura, preciso parar de consultá-la sem ter que fazer deploy."
  escolhi="Flag em memória para ser instantânea, espelhada no banco e relida no boot."
  descartei="Deixar só em memória. A hospedagem gratuita que eu usava desligava o serviço sem tráfego, e a cada religada o interruptor voltava ao padrão."
  custo="Uma leitura a mais ao iniciar, e o mesmo valor guardado em dois lugares, que precisam ficar iguais."
/>

## O trecho que vale ler

Um trecho real do projeto: é ele que relê o interruptor no boot. O comentário explica o porquê.

<Terminal arquivo="cmd/web/main.go">

```go
// O Kill Switch vive em memória para ser instantâneo, mas é gravado em app_settings
// para sobreviver a um restart. Sem esta leitura ele voltaria a false toda vez que o
// serviço subisse — e no free tier do Render isso acontece a cada hibernação, então
// o painel mostraria "ligado" enquanto o backend já estaria consultando a AniList.
if data, _, err := database.Client.From("app_settings").
	Select("value", "exact", false).
	Eq("key", "anilist_force_offline").
	Execute(); err == nil {
	var linhas []struct {
		Value string `json:"value"`
	}
	if err := json.Unmarshal(data, &linhas); err == nil && len(linhas) > 0 {
		if linhas[0].Value == "true" {
			anilist.SetForceOffline(true)
			log.Println("[BOOT] Kill Switch estava ativo: AniList em modo offline forçado.")
		}
	}
} else {
	log.Printf("[BOOT] Não foi possível ler o estado do Kill Switch: %v", err)
}
```

</Terminal>

## O que quebrou

| Sintoma | Causa e correção |
|---|---|
| **Primeiro acesso do dia demorava** | Hibernação do free tier. Migrei para VPS própria, com container sempre de pé. |
| **Quota da API externa estourando em dia de desenvolvimento** | Eu batia na API real rodando local. Criei um cliente falso atrás da mesma interface, ligado por variável de ambiente. |
| **Kill switch que se desligava sozinho a cada hibernação** | Estado só em memória. Passou a ser persistido e relido no boot. |

## O que eu faria diferente

Escreveria testes para a integração com a AniList desde o começo. E guardaria as alterações do banco em arquivos no repositório desde o primeiro dia, em vez de fazê-las direto no painel do Supabase — só passei a fazer isso no meio do projeto.
