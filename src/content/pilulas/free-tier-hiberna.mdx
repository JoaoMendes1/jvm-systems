titulo: O free tier hiberna, e o seu estado em memória some junto
resumo: Uma flag que só existia em memória voltava ao padrão a cada hibernação do host, e o painel mostrava o estado errado.
data: 2026-10-03
tags: [infra]
projeto: anideck
rascunho: false
---

Eu tinha um interruptor no painel do AniDeck para cortar as chamadas à API externa quando ela ficasse instável. Funcionava: eu ligava e as chamadas paravam na hora. No dia seguinte, o painel mostrava o interruptor ligado, e o log mostrava requisições saindo.

A flag morava numa variável de pacote. No free tier, o container hiberna sem tráfego e sobe do zero na próxima visita, com todos os valores padrão de volta. O painel lia o banco; o backend lia a memória. **Havia duas fontes de verdade para o mesmo interruptor, e elas só concordavam até o serviço reiniciar.**

<Callout>**A lição geral:** estado que precisa sobreviver a um restart não pode morar só no processo. E "restart" não é só deploy — é hibernação, OOM kill, migração de host. Todos acontecem sem você olhando.</Callout>

A correção foi gravar a flag numa tabela de configuração e relê-la no boot. A memória continua sendo a fonte de leitura, porque precisa ser instantânea; o banco virou a fonte de verdade na inicialização.

titulo: Erro de serviço externo não é 500
resumo: Quando a API da AniList caiu, o AniDeck respondia 500 numa tela, 502 em outra e 503 numa terceira. O 500 apontava para o lugar errado.
data: 2026-10-04
tags: [go]
projeto: anideck
rascunho: false
---

Em agosto, a API da AniList ficou fora do ar e o AniDeck caiu junto: ranking, busca, deck e detalhes. Um `curl` direto na API, sem passar pelo meu backend, mostrou a causa: ela respondia 403 para todo mundo.

O problema que ficou visível depois foi outro. A mesma falha aparecia com três códigos diferentes: 503 no ranking, 500 nos detalhes e 502 no agente de sugestões do painel.

**O código de status é a primeira pista de quem errou.** `500` diz "o meu servidor quebrou". `503` diz "um serviço do qual eu dependo está indisponível". Respondendo 500, o próprio app apontava a investigação para o meu código, quando a causa era de fora.

<Callout>**A lição geral:** falha de serviço externo vira `503`, com o motivo no corpo da resposta. Assim, o log e a tela já dizem de quem é o problema antes de qualquer investigação.</Callout>

Padronizei os handlers: toda falha da AniList passou a responder 503, com uma mensagem dizendo que a fonte externa está indisponível. A regra também foi escrita no Grimoire, que depende do Google do mesmo jeito.

titulo: O Docker passa por cima do firewall
resumo: O UFW dizia que só três portas estavam abertas, mas a porta de um container respondia de fora. Só descobri testando de fora da máquina.
data: 2026-10-04
tags: [infra, seguranca]
rascunho: false
---

Na migração para a VPS, configurei o UFW para deixar abertas só as portas 22, 80 e 443, e o `ufw status` confirmava. Mesmo assim, quando testei de fora da máquina, a porta 8080 de um container respondia.

O container tinha sido publicado com `ports`, o `-p` do Docker. **Para isso funcionar, o próprio Docker escreve regras no `iptables`, e o tráfego para o container passa por elas, não pelas regras de entrada que o UFW controla.** O firewall não estava errado: ele simplesmente não era consultado para aquele tráfego.

<Callout>**A lição geral:** ler a configuração do firewall não prova que uma porta está fechada. A prova é tentar acessar de fora.</Callout>

A correção foi trocar `ports` por `expose` em todos os containers de aplicação. Com `expose`, a porta só é alcançável pela rede interna do Docker. Quem fala com a internet é o Caddy, nas portas 80 e 443.

A conferência, rodada de outra máquina, tem que falhar:

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://IP_DA_VPS:8080
```

titulo: CREATE TABLE IF NOT EXISTS cria, mas nunca altera
resumo: O Go declarava a coluna como TEXT, o banco tinha uuid, e o boot dizia que estava tudo certo. Por semanas, nada avisou.
data: 2026-10-04
tags: [banco]
projeto: grimoire
rascunho: false
---

No Grimoire, as tabelas eram criadas pelo próprio servidor a cada boot, com `CREATE TABLE IF NOT EXISTS`. Parecia prático: banco vazio ganhava as tabelas sozinho, e banco pronto seguia em frente.

Quando retomei o projeto e comparei o código com o banco, achei uma divergência. O Go declarava `user_id TEXT`, mas no Supabase a coluna de `vocabularies` já era `uuid`, alterada à mão em algum momento. Mesmo assim, o boot anunciava "schema verificado com sucesso".

O motivo está no próprio comando. **`IF NOT EXISTS` só confere se a tabela existe. Se existir, ele não compara nada e não altera nada.** Qualquer mudança de coluna escrita no código depois da primeira execução é ignorada em silêncio.

<Callout>**A lição geral:** um comando que "garante" o schema só garante que a tabela existe, não que ela está do jeito que o código espera. Mudança de coluna é `ALTER TABLE`, num arquivo próprio.</Callout>

A correção foi tirar o DDL do Go. O schema passou a viver em arquivos numerados na pasta `sql/`, aplicados à mão e nunca editados depois de aplicados. O servidor agora só confere se as tabelas existem e se recusa a subir se faltar alguma.
